# 토너먼트 ICM 반영 계획

작성: 2026-11-06. 지금 토너먼트 모드는 모든 계산이 칩 EV 기준이다. 이 계획은 설정에서 ICM 구간을 고르면 프리플랍과 포스트플랍이 그 구간의 상금 구조를 반영해 풀리게 하는 것이다.

## 진행 상황 (2026-11-06)

| 단계 | 상태 |
|---|---|
| 1단계 라이브러리·설정 연결 | 완료 (`feat/icm` 브랜치, 미커밋) |
| 2단계 푸시폴드 ICM | 완료 |
| 3단계 공식 버블 팩터 | 완료, 계수 미검증 |
| 4단계 포스트플랍 | 완료 |
| 5단계 오프라인 솔버 결합 | 해당 없음: 오프라인 솔버 보류 |
| 6단계 좌석별 스택 | 미착수: 앱 전체의 "유효 스택 하나" 전제를 바꾸는 일이라 따로 계획 |

구현하면서 계획과 달라진 점:

- **큰 필드 계산:** 테이블 밖 선수를 묶음으로 근사하지 않는다. 모두 같은 스택이라 서로 구별할 필요가 없어서, "자리 잡은 좌석 집합 + 테이블 밖에서 순위가 정해진 인원"을 상태로 두면 정확히 계산된다(`lib/icm/malmuthHarville.ts`). 400명 남은 경우도 수 ms다.
- **프리셋:** 1,000명 참가, 150명 입상 토너먼트 하나의 구간들이다. 상금은 k^-0.9 분배로 만들었다(1등 14%, 최소 입상 1.5 바이인). 특정 사이트 표가 아니다. 남은 인원: Early 400, Near bubble 170, Bubble 151, In the money 140, Final table 8.
- **버블 팩터 (올인, 모든 스택 동일):** Early 1.18, In the money 1.31, Final table 1.46, Near bubble 1.58, Bubble 1.70. 스택 크기와 무관하다(모두 같은 스택이면 비율만 남음).
- **푸시폴드 방향:** 계획의 "셔브 범위가 좁아짐"은 틀렸다. 같은 스택에서는 콜이 크게 좁아지고, 그 때문에 셔브는 오히려 넓어진다. 15bb SB 셔브 vs BB 콜: 칩 EV 65.0/39.2%, Bubble 97.9/15.8%.
- **공식 구간:** 콜 가격에서 잃는 칩을 버블 팩터 배로 센다. 스택이 한 번에 다 들어가지 않는 콜은 올인 버블 팩터의 절반만 쓴다(`ICM_PARTIAL_RISK_WEIGHT = 0.5`, 공개 차트에 맞춘 값 아님). 40bb BB vs BTN 디펜드: 칩 EV 87.9%, Bubble 78.7%. 모든 스택이 같으면 오픈 쪽 압박이 상쇄되므로 오픈 범위는 바꾸지 않았다.
- **화면:** 설정 창 ICM 항목, 상단 버튼과 출처 라벨에 `ICM <구간>` 표시.
- **포스트플랍 엔진:** 터미널마다 좌석별 "이기면 받는 폭(`won`)·지면 잃는 양(`risked`)"을 받는 `eng_set_payoffs`를 추가했다. 칩 EV에서는 기본값이 팟과 커밋 칩이라 기존 결과가 그대로다. ICM 값은 `lib/postflopSolver/icmPayoffs.ts`가 채우고, 루트에서 팟이 오가는 비율로 나눠 bb처럼 읽힌다. 비김은 이김·짐의 중간값으로 근사한다.
- **정확도 지표:** 엔진의 익스플로이터빌리티는 원래 "두 좌석 최적 대응 이득의 평균"이라 비제로섬에서도 그대로 의미가 있다. 좌석별 이득도 이미 결과에 있다. 그래서 `accuracy-postflop.ts`는 바꾸지 않았다.
- **포스트플랍 효과 (30bb BTN vs BB, K72, 빠른 모드):** 체크 뒤 BTN 벳이 칩 EV 76.1%에서 Bubble 80.5%로 늘었고, 시간(약 2초)과 수렴(0.15%)은 같았다. 리버 올인 장난감 스팟에서는 상금 기준 무차별 빈도와 일치했다(`engine.test.ts`).

## 목표

- 토너먼트를 고르면 설정 창에 **ICM** 항목이 나온다. 캐시를 고르면 Rake 항목이 나오는 지금 방식과 같다.
- 기본값은 지금과 같은 **Chip EV**다. 기존 동작과 테스트는 바뀌지 않는다.
- ICM을 고르면 푸시폴드, 프리플랍 공식, 포스트플랍 솔브가 칩 대신 **상금 기대값($EV)** 기준으로 계산된다.

## ICM이 바꾸는 것

ICM은 칩 스택을 상금 기대값으로 바꾸는 모델이다(Malmuth-Harville). 칩을 잃을 때의 손해가 같은 양을 딸 때의 이득보다 크다. 그래서 콜에 필요한 에쿼티가 올라가고, 공격적인 쪽이 유리해진다.

- **버블 팩터:** 두 사람 사이에서 "잃을 때 $손해 ÷ 딸 때 $이득"이다. 칩 EV에서는 1이고, 버블 근처에서는 1.5~2 이상이 된다.
- **비제로섬:** 두 사람이 싸우면 테이블의 다른 사람도 상금 기대값이 오른다. 그래서 ICM 게임은 두 사람의 이득과 손해가 정확히 상쇄되지 않는다. 솔버 설계에서 가장 중요한 차이다.

## 설정 화면

토너먼트일 때만 `ICM` 항목을 보여 준다. 위치는 Game 아래, Rake 자리다.

```
ICM
 ( ) Chip EV            칩 기준, 지금과 같음 (기본)
 ( ) Early              버블까지 멀음, 약한 ICM
 ( ) Near bubble        버블 직전
 ( ) Bubble             한 명만 떨어지면 입상
 ( ) In the money       입상 직후
 ( ) Final table        파이널 테이블 (8인)
 [ ] 세부 설정 ▸  남은 인원 · 입상 인원 · 상금 분배 · 좌석별 스택
```

- **프리셋:** 구간마다 남은 인원, 입상 인원, 상금 분배를 미리 정해 둔다. 예: Bubble은 남은 인원 = 입상 인원 + 1, 상금은 흔한 MTT 분배표.
  - 프리셋 수치는 구현할 때 공개된 일반 상금 구조에서 정하고 출처를 주석에 남긴다.
- **세부 설정 (2차):** 남은 인원, 입상 인원, 상금 분배를 직접 입력한다. 상금 분배는 평평함·보통·탑헤비 중에서 고르거나 퍼센트를 직접 입력한다.
- **좌석별 스택 (3차):** 처음에는 모든 좌석이 같은 스택(지금의 스택 설정)이라고 가정한다. 좌석별 스택 입력은 앱 전체가 "유효 스택 하나"를 전제하고 있어서 범위가 크다. 마지막 단계로 둔다.
- 레이크처럼 Apply를 누르면 핸드가 다시 시작된다.

## 데이터 구조

- `lib/solveEngine/icm.ts`(새 파일)
  - `IcmSettings`: `{ preset: IcmId, playersLeft, paidPlaces, payouts: number[], stacksBb?: Record<Position, number> }`
  - `ICM_PRESETS`, `CHIP_EV`(기본), `icmById`
  - `RakeSettings`와 같은 방식으로 `app/page.tsx` 상태, `SettingsDialog`, `usePreflopSolve`, 포스트플랍 요청으로 전달한다.

- 캐시 키(`solveCache`, 푸시폴드 결과 캐시)에 ICM 설정을 포함한다.

## ICM 계산 (`lib/icm/`)

- **Malmuth-Harville 정확 계산:** 비트마스크 메모이제이션으로 O(n·2ⁿ)이다. 12명 정도까지는 즉시 계산된다.
- **큰 필드 근사:** 테이블 밖 남은 인원은 실제로 계산할 수 없다. 테이블 밖 선수를 평균 스택을 가진 몇 묶음으로 합쳐 계산한다. 이 부분은 근사라는 점을 문서와 화면에 남긴다.
- **출력 함수:**
  - `icmEquity(stacks, payouts)`: 좌석별 상금 기대값
  - `outcomeValue(stacksAfter)`: 핸드 결과(누가 얼마를 땄는지)별 좌석의 $EV
  - `bubbleFactor(a, b)`: 표시용·공식용
- **테스트:** 손으로 계산할 수 있는 3인 예시(예: 스택 50/30/20, 상금 50/30/20)와 대칭·합계 성질(합 = 총상금, 같은 스택 = 같은 값)로 검증한다.

## 단계별 구현

### 1단계: ICM 라이브러리와 설정 연결

- `lib/icm/`와 테스트를 만든다.
- 설정 창, 요청, API 검증, 캐시 키를 연결한다. 이 단계에서는 ICM을 골라도 결과가 바뀌지 않는다. 화면에 "준비 중" 표시 없이 다음 단계와 같이 배포한다.

### 2단계: 푸시폴드 ICM (≤15bb) — 효과가 가장 큰 곳

- `pushFoldSolver.ts`의 보상 계산을 칩 대신 `outcomeValue`로 바꾼다. 결과 종류(셔버 승·콜러 승·폴드·찬스)가 적어서, 결과별 $EV를 미리 계산하면 기존 반복 구조를 그대로 쓸 수 있다.
- 멀티웨이 올인은 지금처럼 1대1로 근사한다. 다만 다른 좌석의 스택은 ICM 계산에 들어간다.
- 출처 라벨은 `nash-shove-fold`를 유지하고, 요청에 ICM이 있으면 화면에 `ICM`을 함께 표시한다.
- **검증:** 버블에서 셔브·콜 범위가 칩 EV보다 좁아지는지, 큰 스택이 짧은 스택에 더 넓게 셔브하는지, 버블 팩터가 1에 가까운 Early 프리셋은 칩 EV와 거의 같은지 확인한다.

### 3단계: 16bb 이상 프리플랍 공식

- 공식은 균형 계산이 아니라서 ICM을 정확히 넣을 수 없다. **버블 팩터로 가격을 바꾸는 근사**로 넣는다.
  - 콜·디펜스: 필요한 에쿼티를 `팟오즈 × 버블 팩터`로 올린다(`vsOpenContinueThreshold`, `generateVsReraiseScenario`, `generateCallShoveScenario`의 `equityToCall`).
  - 오픈: 뒤 좌석들의 버블 팩터가 크면 스틸이 잘 통하므로 넓히고, 자기 버블 팩터가 크면 좁힌다. 계수는 공개 ICM 차트 비율과 비교해 정한다.
- 출처 라벨은 `heuristic-approx`를 유지한다.
- 오프라인 프리플랍 솔버(`docs/offline-preflop-solver-plan.md`)가 완성되면 이 단계는 그쪽으로 넘어간다. 그 솔버의 터미널 보상을 `outcomeValue`로 바꾸면 된다. 단, 플랍으로 가는 터미널은 칩 결과가 분포로 나오므로 근사가 필요하다(5단계 참고).

### 4단계: 포스트플랍 ICM

- **엔진 변경 (`native/solver/engine.cpp`):** 지금 터미널은 팟 크기 하나만 저장하고 제로섬을 가정한다. ICM에서는 터미널마다 **좌석별로** "이길 때·질 때·비길 때 값" 3개를 저장한다.
  - 값이 핸드가 아니라 승패에만 달려 있으므로, 리버 쇼다운을 O(n)으로 계산하는 지금 기법은 그대로 쓸 수 있다.
- **TypeScript 쪽:** `flattenTree.ts`가 ICM일 때 좌석별 값을 채운다. 남은 스택과 다른 좌석 스택으로 `outcomeValue`를 부른다.
- **정확도 지표:** 비제로섬이라 지금의 익스플로이터빌리티 계산(두 사람 이득의 합)이 맞지 않는다. 좌석별 최적 대응 이득을 따로 보고한다. `scripts/accuracy-postflop.ts`도 같이 고친다.
- **핸드오프:** 프리플랍 ICM 설정과 스택을 포스트플랍 요청에 그대로 넘긴다.
- 엔진과 WASM 재빌드가 필요하므로(`npm run build:wasm`, `check:wasm`), 엔진을 수정 중인 다른 세션과 순서를 맞춘다.

### 5단계: 오프라인 프리플랍 솔버와 결합 (선택)

- 프리플랍 트리의 폴드·올인 터미널은 `outcomeValue`로 정확히 계산된다.
- 플랍 터미널은 플랍 이후 칩 결과가 분포라서, 측정된 칩 기대값을 ICM으로 바꾸려면 근사가 필요하다. 후보는 두 가지다.
  - 팟 주변에서 ICM을 선형화(버블 팩터)
  - 플랍 솔브 자체를 ICM으로 수행
- 포스트플랍 ICM(4단계)이 끝난 뒤 정한다.

### 6단계: 좌석별 스택 입력 (선택)

- 설정에서 좌석마다 스택을 입력하게 한다.
- 유효 스택을 "두 좌석 중 작은 스택"으로 바꾸는 일이 앱 전체(`potState`, `actionSizing`, 핸드오프, 푸시폴드)에 걸쳐 있다. 범위가 커서 따로 계획한다.

| 공개 수치 | 공개된 ICM 푸시폴드 예시(블로그 등)와 방향과 크기 비교. 유료 차트는 데이터로 쓰지 않음 |

## 위험

- **스택 가정:** 모든 좌석이 같은 스택이라는 가정은 실제 ICM 상황과 다르다. ICM의 핵심이 스택 차이인데, 1~5단계는 그것을 반영하지 못한다. 화면에 이 가정을 표시한다.
- **큰 필드 근사:** 테이블 밖 선수를 묶는 근사는 버블 직전처럼 남은 인원이 많은 구간에서 오차가 크다.
- **공식 근사:** 3단계는 균형 계산이 아니다. 출처 라벨로 구분한다.
- **비제로섬 수렴:** 포스트플랍도 2인이지만 ICM에서는 비제로섬이라 CFR 수렴 보장이 약해진다. 좌석별 최적 대응 이득으로 판단한다.
- **작업 충돌:** 푸시폴드, 프리플랍 솔버, `engine.cpp`는 다른 세션의 작업 범위와 겹친다. 시작 전에 미커밋 작업이 정리됐는지 확인한다.
