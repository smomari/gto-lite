# 오프라인 프리플랍 솔버 계획

작성: 2026-11-06. 근사 공식(`lib/heuristicRanges`)으로 만드는 프리플랍 차트를, 개발 PC에서 미리 푼 솔버 결과로 바꾸는 계획이다.

> **보류 (2026-11-06):** 2단계가 통과 기준을 넘지 못했고, 전체 트리의 플랍 측정 비용이 이 PC로 감당하기 어렵다. 지금의 공식 보정을 유지한다. 다시 시작한다면 리버까지 보는 모드로 여러 라운드 수렴 확인, 라운드 사이 값 섞기, 포스트플랍 베팅 사이즈 확대 순서로 원인을 본다.

## 목표

- 16bb 이상 프리플랍 차트를 **오프라인 CFR 솔브 결과**로 바꾼다. 앱은 계산하지 않고 저장된 결과를 읽기만 한다.
- 화면 표시를 `heuristic-approx`에서 솔버 결과로 바꿀 수 있을 만큼 검증한다.
- 외부 유료 차트는 데이터로 쓰지 않는다. GTO Wizard·RYE 수치는 기존처럼 비교 테스트에서만 쓴다.

## 참고한 방식

GTO Wizard의 초기 라이브러리는 MonkerSolver로 큰 프리플랍 트리를 서버에서 오프라인으로 풀어 저장했다. 포스트플랍은 버킷으로 근사했다. 현재 커스텀 솔브는 CFR과 신경망 가치 추정을 결합하고, 플랍까지 가는 인원을 3명 이하로 제한한다. 신경망 방식은 학습 인프라가 필요해 제외하고, 오프라인 솔브와 인원 제한만 따른다.

## 현재 상태 (출발점)

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | `lib/preflopSolver`의 DCFR과 실현율 모델(`realization.ts`). BTN·SB·BB 블라인드 디펜스 트리 | **no-go** (2026-11-04, `scripts/preflop-proto.ts` 주석). 수렴은 되지만, 맞추지 않은 스팟에서 평균 4.9%p, 최대 12.9%p 어긋남. 모델 모양 자체가 문제 |
| 2단계 | 플랍 샘플을 포스트플랍 엔진으로 실제로 풀어 핸드별 값을 측정하고(`flopValues.ts`), 그 값으로 프리플랍을 다시 푸는 반복(`scripts/preflop-measured.ts`) | **불통과** (2026-11-06 측정, 아래). 코드는 미커밋 |

### 2단계 측정 결과 (2026-11-06)

`--flops=30 --rounds=3`, 턴까지만 보는 모드(기본), 4개 스팟. 평균 / 최대 오차(%p, GTO Wizard 대비). 실행 시간 43분(10코어).

| 스팟 | 실현율 모델 | 1라운드 | 2라운드 | 3라운드 |
|---|---|---|---|---|
| MTT 100bb | 1.4 / 3.3 (맞춘 스팟) | 4.1 / 9.1 | 4.0 / 9.4 | 4.3 / 9.6 |
| MTT 40bb | 6.0 / 11.0 | 8.2 / 15.6 | 6.3 / 12.0 | 5.9 / 12.7 |
| MTT 20bb | 4.7 / 12.3 | 1.6 / 4.8 | 3.2 / 7.3 | 3.7 / 9.6 |
| Cash 100bb | 4.7 / 12.9 | 3.6 / 9.6 | 3.2 / 8.2 | 3.4 / 7.7 |

- 토너먼트 스팟 모두 BB가 너무 많이 디펜드한다(3라운드 BB 폴드: 100bb 13.2 vs 22.8, 40bb 0.9 vs 11.9, 20bb 2.7 vs 12.3). 그 결과 BTN 오픈이 5~8%p 좁다.
- 라운드를 반복해도 오차가 줄지 않고, 20bb는 오히려 커진다. 프리플랍·플랍 번갈아 풀기가 수렴하지 않고 진동하는 것으로 보인다.
- 리버까지 보는 모드(`--full`)로 MTT 40bb를 1라운드 돌리면 BB 폴드가 17.5%로 바뀌어 방향이 반대로 넘어간다. 대신 BTN의 3벳 대응이 크게 어긋난다(폴드 35.1 vs 50.8). 평균 / 최대 7.2 / 15.7. 1라운드에 7분, 플랍 터미널 2개 기준이다.
- 비교 기준: 지금 공식은 같은 스팟에서 모든 항목이 3%p 이내다(`gtoWizardMtt.test.ts`, 이 수치에 맞춘 결과).

### 3단계 사전 확인 (2026-11-06)

플랍 2명 제한 규칙으로 전체 좌석 트리를 세었다(`buildPreflopTree`, 첫 오픈 좌석별 트리 합계).

| 형식 | 결정 노드 | 터미널 | 플랍 터미널 |
|---|---|---|---|
| 토너 8인 20bb | 1,435 | 1,918 | 249 |
| 토너 8인 40bb | 2,501 | 3,394 | 454 |
| 토너 8인 100bb | 4,811 | 6,842 | 1,023 |
| 캐시 6인 100bb | 1,582 | 2,366 | 395 |

- 트리 크기는 문제가 아니다. 대신 TypeScript DCFR로 20bb UTG 트리 하나를 2000회 푸는 데 10분이 넘었다(측정과 CPU를 나눠 씀).
- 플랍 측정 비용이 가장 크다. 터미널마다 플랍 30개를 풀면 100bb 한 라운드에 수십 CPU시간 이상이다. 리버까지 보는 모드는 그보다 몇 배 더 든다.

이미 있는 부품:

- 트리 생성: `buildPreflopTree`(`tree.ts`). 앱의 `potState`·`actionSizing`·`rotation`을 그대로 써서 사이즈와 규칙이 앱과 일치한다. 지금은 헤즈업 터미널만 허용한다.
- 풀이: `solvePreflop`(`cfr.ts`, DCFR 2000회). 측정된 플랍 값을 받을 수 있다.
- 검증: 좌석별 최적 대응 이득(`bestResponse.ts`). GTO Wizard 비교 기준표(`lib/solveEngine/gtoWizardMtt.test.ts`, `gtoWizardNl10.test.ts`).

## 진행 조건

**2단계 결과가 이 계획의 전제다.** 2단계가 1단계의 no-go 스팟에서 평균 3%p, 최대 8%p 이내로 들어오면 아래 3단계부터 진행한다. 들어오지 못하면 이 계획을 보류하고 원인부터 본다(플랍 샘플 수, 턴 이후 근사, 사이즈 차이).

2단계 파일은 다른 세션 소유다. 그 작업이 커밋되기 전에는 이 계획의 코드를 시작하지 않는다.

## 3단계: 트리를 전체 좌석으로 넓히기

- **좌석:** 토너먼트 8인, 캐시 6인·8인의 모든 좌석이 오픈할 수 있게 한다.
- **액션:** 앱과 같은 사이즈 하나씩 둔다.
  - 첫 액션: 레이즈·폴드. SB는 림프 포함(`sbCanLimp` 형식)
  - 오픈 상대: 폴드·콜·3벳·올인
  - 3벳 상대: 폴드·콜·4벳·올인
  - 4벳 이상: 폴드·콜·올인
- **플랍 인원 제한:** 처음에는 **헤즈업만** 허용한다. 포스트플랍 엔진이 2인 전용이기 때문이다(`native/solver/engine.cpp`의 `players[2]`). 이미 콜러가 있는 팟에서는 콜을 빼고 3벳·폴드만 남긴다.
  - 예외로 BB의 오버콜은 디펜스 비율에 영향이 커서 3b단계에서 다룬다.
- **3b단계 (3인 팟):** GTO Wizard처럼 플랍 인원을 최대 3명으로 늘린다. 3인 터미널의 값은 엔진으로 측정할 수 없으므로 다음 중 하나로 근사한다. 2단계 결과를 보고 고른다.
  - 3인 올인 에쿼티 × 실현율
  - 헤즈업 측정값의 보정
  - 이 부분은 근사라는 점을 화면에 남긴다.
- **크기 확인:** 8인 100bb 트리의 결정 노드 수와 터미널 수를 먼저 센다. GTO Wizard는 6인 100bb, 사이즈 1개, 콜러 제한 없이 약 62만 노드라고 밝혔다. 우리는 헤즈업 제한으로 이보다 훨씬 작아야 정상이다. 노드가 10만 개를 넘으면 TypeScript DCFR 대신 네이티브 C++ 구현을 검토한다.

## 4단계: 스택·형식별 일괄 솔브

- **솔브할 조합:**
  - 토너먼트 8인: 16, 20, 25, 30, 40, 60, 100bb
  - 캐시 6인·8인: 100bb × 레이크 프리셋
  - 그 사이 스택은 앱의 기존 방식(`anchorsAround`, `lerp`)으로 보간한다.
- **15/16bb 경계:** ≤15bb는 지금처럼 내시 푸시폴드를 쓴다. 다만 솔버가 12~15bb도 풀어서 경계 양쪽 결과가 이어지는지 확인한다. 솔버 쪽이 더 자연스러우면 경계를 낮춘다.
- **실행:** `scripts/preflop-solve-all.ts` 같은 스크립트로 개발 PC에서 돌린다. 플랍 측정은 2단계처럼 워커 프로세스로 병렬 처리한다. 조합별 소요 시간은 2단계 측정 뒤 추정한다(현재 수치 없음).
- **재현성:** 입력(형식, 스택, 레이크, 반복 수, 플랍 샘플 시드, 엔진 버전)을 결과 파일에 함께 기록한다.

## 5단계: 저장 형식과 앱 연결

- **파일:** `data/preflop/<formatId>-<stackBb>bb-<rakeId>.json`
  - 노드 키: 앱의 액션 경로 키(`buildNodeId`)
  - 값: 액션별 169핸드 빈도를 0~255 정수로 저장해 크기를 줄인다
  - 메타데이터: 위 입력값, 좌석별 최적 대응 이득
- **크기 확인:** 한 파일이 1MB를 넘으면 노드를 나누거나 바이너리로 바꾼다. Vercel 함수 번들 한도 안에 들어가야 한다. 지금 에쿼티 행렬은 약 500KB다.
- **API:** `solveActiveSeat`에서 저장된 노드가 있으면 그 결과를 쓰고, 없으면 지금 공식으로 돌아간다. 트리 밖의 경로가 여기에 해당한다(4명 이상 팟, 사이즈가 다른 경로).
- **표시:** 출처 라벨을 새로 둔다(예: `offline-solver`). 화면에 "솔버 결과"와 "근사"를 구분해 보여 준다.
- **포스트플랍 핸드오프:** 솔버 결과의 범위가 그대로 포스트플랍으로 넘어가는지 확인한다(`postflopHandoff.ts`).

## 검증 기준

| 항목 | 기준 |
|---|---|
| 수렴 | 저장하는 모든 솔브에서 좌석별 최적 대응 이득이 0.01bb 이하 (멀티웨이는 수렴 보장이 없어 수치로만 판단) |
| 공개 수치 비교 | `gtoWizardMtt`·`gtoWizardNl10` 기준표의 스팟에서 평균 3%p, 최대 8%p 이내 |
| 핸드 구성 | RYE BTN·UTG 차트와의 Jaccard가 지금 공식(.83, .76)보다 낮아지지 않음 |
| 경계 | 15→16bb, 저장 스택 사이 보간 구간에서 액션 비율이 10%p 이상 끊기지 않음 |
| 앱 | 전체 테스트, `tsc`, `eslint`, 빌드 통과. 브라우저에서 16~100bb 대표 라인과 포스트플랍 진입 확인 |

공식이 더 잘 맞는 스팟이 나오면 그 스팟은 공식을 유지하고 이유를 기록한다.

## 위험

- **3인 이상 수렴:** 이론적 보장이 없다. 좌석별 최적 대응 이득으로만 판단한다.
- **헤즈업 제한의 왜곡:** 콜러가 있는 팟을 막으면 콜드콜과 BB 디펜스가 실제보다 3벳 쪽으로 치우칠 수 있다. 3b단계 전까지 이 스팟은 공식 결과와 비교해 본다.
- **플랍 샘플링 오차:** 30플랍 샘플이 1,755개 플랍 유형을 대표하는지 확인이 필요하다. 샘플 수를 늘리며 결과가 안정되는지 본다.
- **계산 시간:** 조합 수 × 라운드 수 × 플랍 수가 크다. 2단계 측정치로 먼저 추정하고, 너무 크면 스택 수를 줄이고 보간을 늘린다.
- **작업 충돌:** `lib/preflopSolver`와 `native/solver/engine.cpp`는 다른 세션이 수정 중이다. 파일 단위로 나눠 맡고, 커밋 전에 diff 내용을 확인한다.
